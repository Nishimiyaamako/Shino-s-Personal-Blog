# 前后端类型契约加固 — 技术设计

## 防线结构

```
后端（Rust）                         前端（TS）
tests/api_compat.rs          ────   vitest 夹具测试
  递归键集断言（响应侧）               递归键集断言（契约侧）
  "实际响应键 ⊆ 契约键"                "契约键 ⊆ fixture 键"
        │                                   ▲
        └── 同一份响应形状（JSON） ──────────┘
        fixtures/*.json（前端侧快照）
```

- 后端侧：对每个公开端点构造请求 → 断言响应 JSON 的递归键集合与契约（注释中声明的 TS 结构对应）一致。方向 `⊆`：捕获"实现漂移出契约"（多出未声明字段/改名）。
- 前端侧：fixture JSON 声明为接口类型（编译期 `as` 检查）；运行时递归收集 fixture 键集与接口键集比对，方向 `⊆`：捕获"契约声明了但快照/后端没有的字段"。
- 双方向合起来构成完整闭环：任一侧字段增删，至少一侧测试失败。

## 实现要点

1. 先读 `tests/api_compat.rs` 现状：已有断言模式（状态码/字段抽样？），在现有风格上扩展递归键集断言，避免另起炉灶。
2. 后端键集断言辅助函数：
   ```rust
   fn assert_json_shape(value: &serde_json::Value, expected: &serde_json::Value)
   // 递归：object 键集相等（sorted compare）；array 取首元素递归；标量类型匹配
   ```
   期望形状从真实响应快照得来（先跑一次记录），或按 models.rs 结构手写——推荐以"跑通后固化的快照"为基线，防止断言本身臆造。
3. 前端夹具：`frontend/src/` 建 `__fixtures__/`（或测试就近目录），每个 fixture 注释标注来源（对应 api_compat.rs 场景 + models.rs 结构名）。测试用 `Object.keys` 递归比较，类型用 `satisfies` 风格编译期校验。
4. 前后端各自独立成测试，不共享文件（避免跨语言构建依赖）。

## 兼容性

- 不改生产代码；不改 API 契约；新增测试文件与 fixture 均为新增资产。
- 若实现中发现真实漂移（如某字段两端确实不一致）→ 记录为 P1 bug 单独处理，不在本任务修复（除非是纯测试夹具问题）。
